# Idea Research: Live pipeline flow UI

- **Slug**: live-pipeline-flow-ui
- **Created**: 2026-09-09
- **Evidence confidence (overall)**: medium

## Users & Demand

- The owner is currently only able to listen to sample audio because the app is running in **stub/sample mode**; they want the full learning pipeline to be visible end-to-end (transcript → summary → judge score/rationale → overall dashboard) and to be able to compare outputs across agents.  
  - [source: apps/voiceFaithfulness/frontend/src/App.tsx (providersMode defaults to `"stub"` and shows stub banners)]

- The UI already supports viewing a transcript and summary for the **most recent** pipeline run, but it does not show the *reason* behind the faithfulness score, and it only keeps one run snapshot in state.  
  - [source: apps/voiceFaithfulness/frontend/src/App.tsx (render: transcript/summary; score is shown without rationale)]
  - [source: apps/voiceFaithfulness/frontend/src/App.tsx (state: `const [run, setRun] = useState<Run | null>(null)`; no run history render)]

## Prior Art

- Existing voiceFaithfulness implementation (v1 spec / 001 feature track) already implements the basic learning pipeline and exposes:
  - transcription agent selection (`/api/agents/transcription`)
  - judge agent selection (`/api/agents/judge`)
  - transcript + summary display for the completed run
  - per-recording score rows and overall aggregate  
  - [source: apps/voiceFaithfulness/specs/001-llm-judge-dashboard/spec.md]
  - [source: apps/voiceFaithfulness/frontend/src/App.tsx]

- Summary agent selection is **intentionally not present** in v1: the summarizer is fixed/configured by the product.  
  - [source: apps/voiceFaithfulness/backend/app/providers/catalog.py (`SUMMARIZER_ID`, fixed; comment “not learner-selectable in v1”)]
  - [source: apps/voiceFaithfulness/specs/001-llm-judge-dashboard/spec.md (FR-017: summarizer fixed/configured; “add only via later spec amendment if desired.”)]

- Judge score rationales are produced by the backend runner but are **not currently surfaced in the frontend**. The backend stores `run["score"]["rationale"]`, while the frontend `Run.score` type and rendering only include `value` + `judge_agent_id`.  
  - [source: apps/voiceFaithfulness/backend/app/domain/runner.py (`run["score"] = { value, judge_agent_id, rationale }`)]
  - [source: apps/voiceFaithfulness/frontend/src/App.tsx (`type Run` score omits rationale; UI prints score value/judge+STT only)]

- There is an API contract mismatch risk: the Spec “contracts/api.md” states score shape as `{ value, judge_agent_id }` and does not mention rationale, while the runner includes rationale.  
  - [source: apps/voiceFaithfulness/specs/001-llm-judge-dashboard/contracts/api.md (GET /runs: `score: { "value": 0-100, "judge_agent_id": "…" }`)]
  - [source: apps/voiceFaithfulness/backend/app/domain/runner.py (rationale returned/persisted in run score)]

## Market & Context

- Assumption: For an educational “LLM-as-judge” demo, users generally expect to understand *why* a score was produced and to compare outputs across multiple model/provider configurations.
  - Marked as ASSUMPTION (no external user study citations collected in this repo-based research pass).

## Data & Constraints

- Stub vs live provider mode:
  - Frontend defaults to `"stub"` mode and shows a banner warning that transcript/score are demo placeholders unless live providers are active.
  - Backend provider mocks (MockSTT/MockSummarizer/MockJudge) return deterministic text and a constant mock score/rationale.
  - Live Groq judge requires `GROQ_API_KEY` and is rate-limit aware.  
  - [source: apps/voiceFaithfulness/frontend/src/App.tsx (providersMode default; stub/live banners)]
  - [source: apps/voiceFaithfulness/backend/app/providers/mocks.py]
  - [source: apps/voiceFaithfulness/backend/app/providers/groq_judge.py]

- One-run-at-a-time constraint:
  - Backend store tracks `active_run_id` and rejects starting a new run while one is active.  
  - [source: apps/voiceFaithfulness/backend/app/domain/store.py]
  - [source: apps/voiceFaithfulness/backend/app/api/runs.py (409 run_in_progress)]

- Run history & aggregate scope:
  - Store keeps an in-memory `runs` map and a `scores` list, but the SPA only holds the most recently started/pulled `run` snapshot in UI state.
  - Overall dashboard percent is the arithmetic mean of completed scores currently in the in-memory store.  
  - [source: apps/voiceFaithfulness/backend/app/domain/store.py (RunStore.runs/scores; list_runs/list_scores)]
  - [source: apps/voiceFaithfulness/backend/app/domain/aggregate.py (fmean mean of completed scores)]
  - [source: apps/voiceFaithfulness/frontend/src/App.tsx (no run-history list render)]

## Evidence Against the Idea

- Adding “different summaries generated by different agents” conflicts with current v1 design where the summarizer is fixed (`SUMMARIZER_ID`) and explicitly not user-selectable (FR-017). Implementing this likely requires new product-configured summarizer options or making summarizer selectable and extending the run pipeline accordingly.  
  - [source: apps/voiceFaithfulness/specs/001-llm-judge-dashboard/spec.md (FR-017)]
  - [source: apps/voiceFaithfulness/backend/app/providers/catalog.py]

- “Why the score was stated as it was” currently requires UI work: the backend produces a rationale, but the frontend data model and rendering don’t include/display it, and the API contract doc also omits rationale. This could require coordinated updates across backend response models, frontend types, and the spec contract.  
  - [source: apps/voiceFaithfulness/backend/app/domain/runner.py]
  - [source: apps/voiceFaithfulness/frontend/src/App.tsx]
  - [source: apps/voiceFaithfulness/specs/001-llm-judge-dashboard/contracts/api.md]

- A left-to-right “flow” UI may reduce clarity on smaller screens; the current SPA already uses a vertical sectioning layout that likely helps mobile readability. If horizontal flow is required on desktop, it may require responsive layout work and additional QA.  
  - [source: apps/voiceFaithfulness/frontend/src/App.tsx (single-column layout with section blocks)]

- Complexity/cost/rate-limits risk: enabling multiple agent combinations and generating multiple summaries/judgements could multiply provider calls and increase the probability of hitting free-tier limits (backend already supports `rate_limited` error handling).  
  - [source: apps/voiceFaithfulness/backend/app/api/runs.py (429 for rate_limited)]
  - [source: apps/voiceFaithfulness/backend/app/providers/groq_judge.py (429 → RateLimitedError)]

## Gaps & Open Questions

- [NEEDS CLARIFICATION: “Different summaries generated by different agents” — should this mean summarizer selection (new dropdown + rerun pipeline per summarizer), or does it accept “different transcript agents produce different summaries” as the comparison axis?]
 - The transcript agent will transcribe the audio and generate a summary. The judge agent will judge the summary and provide a score and rationale.

- [NEEDS CLARIFICATION: “Stronger agent attempt to judge the summary” — should judge agent be restricted to a “stronger than STT” policy, or should any chosen judge be allowed (current UI already allows any judge agent selection from catalog)?]
  - Any chosen judge is allowed but the stronger judge should be highlighted relative to the transcript agent that produced the summary. 
  
- [NEEDS CLARIFICATION: Judge rationale format — should the UI show:
  - raw rationale text,
  - parsed “criteria + explanation”,
  - or a structured set of bullet reasons?]
  - All of the above should be allowed but displayed in layers. As the user hovers over the summary, the rationale should be displayed in a tooltip.

- [NEEDS CLARIFICATION: Run history retention — should the app keep a multi-run timeline/history view within the session, or only support per-run comparison for the current selected agent combination?]
  - The app should keep a multi-run timeline/history view within the session.

- [NEEDS CLARIFICATION: Left-to-right flow — exact layout behavior on desktop vs mobile (swap columns, collapsible sections, etc.).]
  - Left-to-right in desktop view. 
  - Vertical in mobile view.
  - The option to switch between desktop and mobile view should be available.
